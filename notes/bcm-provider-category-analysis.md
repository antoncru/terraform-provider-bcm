# BCM Provider Category Fields Analysis

How the Terraform provider builds the `addCategory` and `updateCategory` JSON-RPC payloads, field by field, compared against what BCM returns. Based on analysis of 17 live category entities from `categories.json`.

**Source code:** `resource_cmdevice_category.go` (`buildAPIEntity`, `readCategory`)
**Reference data:** `hashi-poc/casper-test-templates/bcm10-casper/categories.json`

---

## 1. BCM Patch Semantics (Categories)

Categories follow the same patch semantics as devices and networks:

| Payload pattern | BCM behavior |
|-----------------|-------------|
| Key absent from JSON | **Keep existing value** (no change) |
| Key present with value | Set to that value |
| Key present with `""` / `0` / `false` | Set to empty/zero/false |
| Array field (fsmounts, roles, services, etc.) | **Full replacement** -- send complete array |

**Provider strategy:** `Set*Field` helpers omit null/unknown fields. On create, BCM applies defaults for omitted fields. On update, BCM preserves existing values for omitted fields.

### Naming conventions

Three naming conventions are bridged by the Go model struct:

| Layer | Convention | Example | Mapped by |
|-------|-----------|---------|-----------|
| BCM API (JSON-RPC) | camelCase | `cpuspeedGovernor` | String key in `SetStringField` / `getStringValue` |
| Go struct | PascalCase | `CpuspeedGovernor` | Direct field access |
| HCL / Terraform | snake_case | `cpuspeed_governor` | `tfsdk` struct tag |

The `tfsdk:"cpuspeed_governor"` struct tag connects Go ↔ HCL. The `buildAPIEntity` and `readCategory` functions connect Go ↔ BCM API using camelCase string keys.

## 3. Schema Design Decisions

### Plan Modifiers: `UseStateForUnknown`

`cpuspeed_governor` and `extra_values` both use `stringplanmodifier.UseStateForUnknown()`:

| Create (no prior state) | Subsequent plans (prior state exists) |
|---|---|
| Plan value = `Unknown` | Plan value = prior state value |
| `Set*Field` skips it (omitted from payload) | `Set*Field` sends it (if not null) |
| BCM uses its default (`""` for cpuspeed_governor) | BCM receives the stored value |
| `readCategory` reads BCM's actual value into state | No diff unless config changes |

This prevents false drift: BCM defaults the field, provider reads it back, and on the next plan the state value is reused rather than showing `Unknown`.

### Optional vs Optional+Computed

Most category fields are **Optional** (not Computed). This is because category fields rarely have server-set defaults that the user needs to see. The exceptions:

- `cpuspeed_governor` -- BCM defaults to `""` (empty = system default). Optional+Computed so BCM's value is visible in state.
- `extra_values` -- Computed-only. BCM internal metadata, never sent by provider.

Fields like `boot_loader` and `install_mode` are **Optional** (without Computed) even though BCM has defaults. This means if the user omits them from config, they won't appear in state. This is acceptable because:
1. BCM's defaults are well-known (`"SYSLINUX"`, `"AUTO"`)
2. The user either wants to set them explicitly or doesn't care about the defaults

### Array fields: full replacement semantics

All array fields (fsmounts, fsexports, roles, services, gpu_settings, static_routes, modules, name_servers, search_domains, time_servers) use BCM's **full replacement** semantics:

- If the field is set in config, the entire array is sent to BCM (replacing whatever was there)
- If the field is null/unknown (omitted from config), the field is not sent (BCM keeps existing values)

### Non-persisted category fields (BCM quirk)

BCM accepts but doesn't store certain category fields. The provider preserves plan values for these:

| Field | BCM Behavior | Provider Workaround |
|---|---|---|
| `static_routes` | Accepted but not returned | Preserve plan values |
| `fsexports` | Accepted but not returned | Preserve plan values |
| `roles` | Accepted; UUIDs may not persist | Generate UUIDs locally, merge with API |
| `gpu_settings` | Accepted but not returned | Preserve plan values |
| `services` | Accepted but not returned | Preserve plan values |

See [Issue #73](https://github.com/hashi-demo-lab/terraform-provider-bcm/issues/73).

## 5. Bug Fix: fsmount Field Mapping

### The problem

The `readCategory` function was reading fsmount fields using wrong BCM field names:

| Read function used | BCM actually returns |
|---|---|
| `"path"` | `"mountpoint"` |
| `"type"` | `"filesystem"` |
| `"options"` | `"mountoptions"` |

This meant `getStringValue(mountMap, "path")` returned null because the BCM response key is `"mountpoint"`.

The `buildAPIEntity` function had the same issue -- it sent `"path"`, `"type"`, `"options"` instead of BCM's canonical field names.

### Evidence

From `categories.json` fsmount entries:

```json
{
  "baseType": "FSMount",
  "childType": "",
  "device": "none",
  "dump": false,
  "extra_values": null,
  "filesystem": "devpts",
  "fsck": "NONE",
  "modified": false,
  "mountoptions": "gid=5,mode=620",
  "mountpoint": "/dev/pts",
  "rdma": false,
  "revision": "",
  "to_be_removed": false,
  "uuid": "61582870-142d-4a86-ba65-78b74bb899ca"
}
```

### The fix

**Build side** (`buildAPIEntity`): Changed to canonical names:

```go
mountMap := map[string]interface{}{
    "baseType":   "FSMount",
    "device":     mount.Device.ValueString(),
    "mountpoint": mount.Mountpoint.ValueString(),
    "filesystem": mount.Filesystem.ValueString(),
}
SetStringField(mountMap, "mountoptions", mount.MountOptions)
```

**Read side** (`readCategory`): Changed to canonical names:

```go
"mountpoint":   getStringValue(mountMap, "mountpoint"),
"filesystem":   getStringValue(mountMap, "filesystem"),
"mountoptions": getStringValue(mountMap, "mountoptions"),
```

## 6. API Call Sequence

### When `buildAPIEntity` is called

| CRUD method | When | What it does |
|---|---|---|
| **Create** | Before `addCategory` | Converts plan → BCM entity with generated UUID |
| **Update** | Before `updateCategory` | Converts plan → BCM entity with existing UUID |
| **Read** | Never | Read uses `getCategory` directly |
| **Delete** | Never | Delete uses `removeCategory` with UUID |

### When `readCategory` is called

| CRUD method | When | What it does |
|---|---|---|
| **Create** | After `addCategory` | Populates `&plan` from BCM's read-back, then `resp.State.Set` |
| **Read** | During plan refresh | Populates `&state` from BCM's response, updates `.tfstate` |
| **Update** | After `updateCategory` | Populates `&plan` from BCM's read-back, then `resp.State.Set` |
| **Delete** | Never | Nothing to read back |

### Validation

Categories use `CMDevice.validateCategory` for pre-flight validation:

```go
validationErrors, _ := r.client.ValidateEntity(ctx, "CMDevice", "validateCategory", entity, isCreate)
```

Minimal payload for creating a new category (fields omitted = BCM defaults):

```json
{
  "service": "cmdevice",
  "call": "addCategory",
  "args": [{
    "baseType": "Category",
    "childType": "",
    "modified": true,
    "to_be_removed": false,
    "revision": "",
    "uuid": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
    "name": "test-category",
    "managementNetwork": "161d0552-5b1a-44b3-8ba0-abbadd22db73",
    "softwareImageProxy": {
      "baseType": "SoftwareImageProxy",
      "childType": "",
      "modified": true,
      "to_be_removed": false,
      "revision": "",
      "uuid": "ffffffff-gggg-hhhh-iiii-jjjjjjjjjjjj",
      "parentSoftwareImage": "b00d5a12-5f6e-4092-b25e-901be71165df"
    }
  }, false]
}
```

BCM will apply defaults for all omitted fields:
- `bootLoader` → `"SYSLINUX"`
- `bootLoaderProtocol` → `"HTTP"`
- `installMode` → `"AUTO"`
- `newNodeInstallMode` → `"FULL"`
- `interactiveUser` → `"ALWAYS"`
- `fips` → `"NO"`
- `cpuspeedGovernor` → `""`
- `defaultGateway` → `"0.0.0.0"`
- `fsmounts` → default system mounts (devpts, proc, sysfs, tmpfs, nfs)
- `excludeList*` → default rsync rules
