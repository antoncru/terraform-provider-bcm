# BCM Provider Network Fields Analysis

How the Terraform provider builds the `addNetwork` and `updateNetwork` JSON-RPC payloads, field by field, compared against what BCM returns. Based on analysis of 8 live network entities from `networks.json`.

**Source code:** `resource_cmnet_network.go` (`buildNetworkAPIEntity`, `mapNetworkAPIResponseToState`)
**Reference data:** `hashi-poc/casper-test-templates/bcm10-casper/networks.json`

---

## 1. BCM Patch Semantics (Networks)

Networks follow the same patch semantics as devices:

| Payload pattern | BCM behavior |
|-----------------|-------------|
| Key absent from JSON | **Keep existing value** (no change) |
| Key present with value | Set to that value |
| Key present with `""` / `0` / `false` | Set to empty/zero/false |

**Provider strategy:** `Set*Field` helpers omit null/unknown fields. On create, BCM applies defaults for omitted fields. On update, BCM preserves existing values for omitted fields.

### Naming conventions

Three naming conventions are bridged by the Go model struct:

| Layer | Convention | Example | Mapped by |
|-------|-----------|---------|-----------|
| BCM API (JSON-RPC) | camelCase | `allowAutosign` | String key in `SetStringField` / `getStringValue` |
| Go struct | PascalCase | `AllowAutosign` | Direct field access |
| HCL / Terraform | snake_case | `allow_autosign` | `tfsdk` struct tag |

The `tfsdk:"allow_autosign"` struct tag connects Go ↔ HCL. The `buildNetworkAPIEntity` and `mapNetworkAPIResponseToState` functions connect Go ↔ BCM API using camelCase string keys.

## 3. Terraform Plan/Apply Lifecycle

Terraform operates in two distinct phases. Understanding where data comes from at each phase is essential for reading the provider code.

### Phase 1: Plan (`terraform plan`)

Terraform computes a **plan** -- a diff between the desired state (HCL config) and the current state (`.tfstate` file). No API calls to BCM happen during planning (except for data sources).

```
HCL Config + Prior State → Terraform Core → Planned Changes
```

For each resource attribute, Terraform resolves a planned value:

| Situation | Plan value | Meaning |
|-----------|-----------|---------|
| User sets `name = "testnet"` | `StringValue("testnet")` | Known value from config |
| User omits an Optional field | `Null` | "Not configured" |
| User omits an Optional+Computed field | `Unknown` | "Will be determined during apply" |
| Computed field (e.g., `uuid`) | `Unknown` | "Provider will compute this" |
| Optional+Computed field with `UseStateForUnknown` + prior state exists | Prior state value | "Keep what we had" |

Plan modifiers run during this phase to adjust planned values before the diff is shown to the user.

### Phase 2: Apply (`terraform apply`)

After the user approves the plan, Terraform calls the provider's CRUD methods. The provider receives the **plan** as input:

```go
var plan CMNetNetworkResourceModel
resp.Diagnostics.Append(req.Plan.Get(ctx, &plan)...)
// plan is now populated from the planned values above
```

The `req.Plan.Get()` call uses the `tfsdk` struct tags to map HCL attribute names to Go struct fields. Each field is a `types.String` / `types.Bool` / `types.Int64` that can be in one of three states: **Value** (known), **Null**, or **Unknown**.

The provider then builds the API payload from the plan:

```go
entity, err := buildNetworkAPIEntity(ctx, &plan, "")
// plan is passed as "data" parameter
// SetStringField checks: if Null or Unknown → skip (omit from JSON)
//                        if Value → include in JSON
```

After the API call, the provider reads back from BCM and writes to **state**:

```go
mapNetworkAPIResponseToState(ctx, bcmResponse, &plan)  // populate from BCM
resp.State.Set(ctx, &plan)                              // write to .tfstate
```

### Data flow summary

```
terraform plan:
  HCL config ──→ Plan (with modifiers) ──→ Show diff to user

terraform apply:
  Plan ──→ req.Plan.Get(ctx, &plan)
       ──→ buildNetworkAPIEntity(plan)     ──→ JSON-RPC to BCM
       ──→ mapNetworkAPIResponseToState()  ──→ resp.State.Set()
       ──→ .tfstate file updated

Next terraform plan:
  HCL config + .tfstate ──→ Plan (UseStateForUnknown copies from .tfstate)
                         ──→ Diff (should be empty if idempotent)
```

### Where each CRUD method gets its data

| Method | Input source | Provider reads via | Output |
|--------|-------------|-------------------|--------|
| **Create** | Plan (from HCL config) | `req.Plan.Get(ctx, &plan)` | `resp.State.Set(ctx, &plan)` |
| **Read** | Prior state | `req.State.Get(ctx, &state)` | `resp.State.Set(ctx, &state)` |
| **Update** | Plan + Prior state | `req.Plan.Get` + `req.State.Get` | `resp.State.Set(ctx, &plan)` |
| **Delete** | Prior state | `req.State.Get(ctx, &state)` | State removed automatically |
| **Import** | User-provided ID | `req.ImportStateRequest.ID` | `resp.State.Set` (via Read) |

Update reads both: the **plan** has the new desired values, the **state** has the current `revision` for concurrency control.

### When `mapNetworkAPIResponseToState` is called

This function converts BCM JSON → Go struct → Terraform state. It's called after every API read-back:

| CRUD method | When | What it does |
|-------------|------|-------------|
| **Create** | After `addNetwork` + `getNetwork` | Populates `&plan` from BCM's read-back, then `resp.State.Set(ctx, &plan)` writes to `.tfstate` |
| **Read** | During plan refresh | Populates `&state` from BCM's response, then `resp.State.Set(ctx, &state)` updates `.tfstate` |
| **Update** | After `updateNetwork` + `getNetwork` | Populates `&plan` from BCM's read-back, then `resp.State.Set(ctx, &plan)` writes to `.tfstate` |
| **Delete** | Never | Nothing to read back -- resource is gone |

### When `buildNetworkAPIEntity` is called

This function converts Go struct → BCM JSON entity. It's called only for Create and Update:

| CRUD method | Call | UUID parameter | Effect |
|-------------|------|---------------|--------|
| **Create** | `buildNetworkAPIEntity(ctx, &plan, "")` | Empty string | Generates a fresh UUID via `generateUUID()` |
| **Update** | `buildNetworkAPIEntity(ctx, &plan, plan.UUID.ValueString())` | Existing UUID | Uses the UUID from state |
| **Read** | Not called | — | Only needs the UUID string for `getNetwork` lookup |
| **Delete** | Not called | — | Only needs the UUID string for `removeNetwork` |

After `buildNetworkAPIEntity` returns, both Create and Update send the entity through `validateNetwork` (pre-flight check) before the actual API call (`addNetwork` or `updateNetwork`).

## 4. Schema Design Decisions

### Plan modifiers and `UseStateForUnknown`

Plan modifiers are hooks that run during `terraform plan` to customize how Terraform computes the planned value for an attribute **before** any API call. All Optional+Computed fields in this resource use `UseStateForUnknown()`, which says: "If the planned value would be Unknown (user didn't set it), copy the value from prior state instead."

Without this modifier, Optional+Computed fields cause false drift:

| Step | Without modifier | With `UseStateForUnknown` |
|------|-----------------|--------------------------|
| Create | User omits field. Plan=Unknown. BCM defaults to `"AUTOMATIC"`. State=`"AUTOMATIC"`. | Same. |
| Next plan | Plan=Unknown. Terraform sees Unknown vs `"AUTOMATIC"` in state → **proposes change (false drift)**. | Modifier copies state → Plan=`"AUTOMATIC"`. Matches state → **no drift**. |

On create (no prior state), `UseStateForUnknown` has nothing to copy, so the plan value stays Unknown. This is correct -- the Unknown flows through to `SetStringField` / `SetBoolField`, which skip Unknown values (same as null), so the field is omitted from the payload. BCM applies its default, the follow-up `getNetwork` read populates the actual value into state, and from that point forward the modifier has something to copy.

| Lifecycle | Prior state? | Modifier does | Plan value | Result |
|-----------|-------------|---------------|------------|--------|
| Create | No | Nothing | Unknown | Field omitted → BCM defaults → read-back populates state |
| Update | Yes | Copies prior state | Prior value | Field sent (or omitted if null) → no false drift |
| Import | No | Nothing | Unknown | Read from BCM populates state from scratch |

### Optional vs Optional+Computed

| Pattern | Fields | Behavior when user omits from config |
|---------|--------|--------------------------------------|
| **Optional** | `gateway`, `mtu`, `domain_name`, `dhcp_range_start`, `dhcp_range_end`, `notes`, `subnet` | Plan value is null. BCM defaults. Read maps default to null (sentinel-to-null). No drift. |
| **Optional+Computed** | `network_type`, `management`, `bootable`, `allow_autosign`, `generate_dns_zone`, `lock_down_dhcpd`, `disable_automatic_exports`, `exclude_from_search_domain`, `search_domain_index`, `ipv6_enabled`, `ipv6_base_address`, `ipv6_gateway`, `ipv6_netmask_bits`, `ec2_availability_zone`, `ec2_string`, `cloud_subnet_id` | Plan value is Unknown on create. `UseStateForUnknown` copies prior state on update. BCM value read as-is. No drift. |
| **Computed** | `uuid`, `id`, `base_address`, `netmask_bits`, `dhcp_enabled`, `base_type`, `child_type`, `revision`, `modified`, `to_be_removed`, `extra_values` | Provider or BCM computes the value. User cannot set it. |

### Sentinel-to-null mapping (Optional fields only)

For Optional-only fields, BCM returns sentinel defaults that would cause false drift against a null config value. The read function maps these sentinels to null:

| Field | Sentinel | Mapped to |
|-------|----------|-----------|
| `gateway` | `"0.0.0.0"` or `""` | `types.StringNull()` |
| `mtu` | `1500` | `types.Int64Null()` |
| `domain_name` | `""` | `types.StringNull()` |
| `dhcp_range_start` | `"0.0.0.0"` or `""` | `types.StringNull()` |
| `dhcp_range_end` | `"0.0.0.0"` or `""` | `types.StringNull()` |
| `notes` | `""` | `types.StringNull()` |
| `base_address` | `"0.0.0.0"` or `""` | `types.StringNull()` |

Optional+Computed fields do NOT need sentinel-to-null mapping because `UseStateForUnknown` handles drift prevention.

### Special case: MTU 1500

BCM defaults MTU to 1500 and the read function maps 1500 to null. If a user explicitly sets `mtu = 1500`, this would be lost on read. The Create, Read, and Update functions include a special case to preserve the planned MTU when it equals 1500:

```go
if !plannedMTU.IsNull() && !plannedMTU.IsUnknown() && plannedMTU.ValueInt64() == 1500 && plan.MTU.IsNull() {
    plan.MTU = plannedMTU
}
```

### Special case: domain_name "cluster.local"

Similar logic prevents the BCM default `"cluster.local"` from appearing in state when the user didn't set `domain_name`:

```go
if plannedDomainName.IsNull() && !plan.DomainName.IsNull() && plan.DomainName.ValueString() == "cluster.local" {
    plan.DomainName = types.StringNull()
}
```

## 5. API Call Sequence

### Create (`addNetwork`)

1. `CMNet.validateNetwork` — pre-flight validation (isCreate=true)
2. `cmnet.addNetwork` — creates network entity
3. `cmnet.getNetwork` — read-back to populate state

### Update (`updateNetwork`)

1. `CMNet.validateNetwork` — pre-flight validation (isCreate=false)
2. `cmnet.updateNetwork` — updates network entity (force=false)
3. `cmnet.getNetwork` — read-back to populate state

### Delete (`removeNetwork`)

1. `cmnet.removeNetwork` — removes network by UUID

## 8. Network Type Variations

From the 8 networks in `networks.json`:

| Network | Type | Management | Bootable | MTU | DHCP |
|---------|------|------------|----------|-----|------|
| dgxnet | INTERNAL | true | true | 1500 | yes (71-80) |
| vlan104 | INTERNAL | true | true | 1500 | yes (52-56) |
| ipminet | INTERNAL | false | false | 1500 | yes (20-40) |
| ibnetcompute | INTERNAL | false | false | 4092 | no |
| internalnet | INTERNAL | true | true | 1500 | yes (11-20) |
| vlan103 | INTERNAL | true | true | 1500 | yes (36-40) |
| ibnetstorage | INTERNAL | false | false | 4096 | no |
| globalnet | GLOBAL | false | false | 1500 | no |

Key observations:
- `management=true` networks are always `bootable=true` (management implies PXE boot capability)
- InfiniBand networks (`ibnet*`) use high MTU (4092/4096) and no DHCP
- `GLOBAL` network has `baseAddress=0.0.0.0` and `netmaskBits=0` (no addressing)
- IPMI network is neither management nor bootable (out-of-band management)
